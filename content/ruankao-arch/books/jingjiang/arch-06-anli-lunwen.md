## 考点梳理

### 6.1 案例分析四类题型与模板

| 题型 | 典型问法 | 答题模板 |
|------|---------|---------|
| **架构风格选择** | "应采用何种架构风格？说明理由" | 亮风格 → 结合**质量属性/约束**给理由 → 说明实现要点与风险 |
| **质量属性分析** | "该系统最需关注哪些质量属性？如何设计" | 列属性（性能/可用性/安全性…）→ 对应**战术**（缓存/冗余/加密） → 给出度量指标 |
| **系统设计补全** | "请补充缺失的模块/流程" | 按分层或服务划分补全 → 说明模块职责与交互 |
| **技术选型对比** | "比较 A 与 B 方案并选择" | 列对比维度（性能/成本/复杂度/可维护性）→ 结合场景选择并说明理由 |

**通用要点**：分点作答、**术语规范**、**理由必须落到质量属性或约束**（这是架构案例的评分核心），必要时给出量化指标（QPS、响应时间、可用性）。

### 6.2 架构论文怎么写（与高项论文的区别）

- **相同**：四段式（背景 → 方案与实施 → 效果与问题 → 总结）；
- **不同**：架构论文要求**技术深度**——必须写清**技术选型与理由**、**架构分层/组件划分**、**关键技术机制**（缓存、消息、负载均衡、容灾等）与**量化效果**。

**推荐结构（120 分钟、约 2000–2500 字）**：

| 段落 | 字数（示例） | 内容 |
|------|------------|------|
| 项目背景 | 300 | 系统规模（用户量/数据量/QPS）、我的角色（架构师） |
| 架构方案 | 800 | 分层/服务划分 + 架构图描述 + 关键技术机制 |
| 技术选型与理由 | 500 | 为什么选该架构风格/中间件/存储（对标质量属性） |
| 实施效果与问题 | 400 | 量化指标（响应时间、可用性、成本）+ 遇到问题与解决 |
| 总结 | 200 | 经验、不足与改进 |

### 6.3 常见论文主题（提前准备素材）

微服务架构设计与落地 / 高可用系统设计 / 系统性能优化 / 数据架构与分库分表 / 云原生与容器化 / 安全架构设计 / 遗留系统重构与迁移。

**素材卡准备法**：每个主题准备"技术方案 + 选型理由 + 量化效果 + 一个问题与解决"，共 5–7 张，考场按题目组合。

## 🧠 记忆工具箱

### 口诀速记

- 案例作答：**亮方案 → 给理由（质量属性）→ 讲实现 → 说风险**；
- 论文骨架：**背景、方案、选型、效果、总结**；
- 架构论文加分项：**量化指标 + 质量属性对应 + 架构图描述**；
- 选型三维度：**性能、成本、可维护性**（再加可用性与扩展性）。

### 例题（带解析）

**例题 1**：架构案例题要求"选择架构风格并说明理由"。最易得分的作答方式是？
A. 只写"采用微服务架构"　B. 明确所选风格，并结合性能、可用性、可修改性等质量属性与项目约束说明理由　C. 罗列所有架构风格　D. 只写技术栈名称
**答案 B**。解析：架构案例的核心是"决策 + 依据"：所选风格必须与题干的质量属性诉求和约束对应，只给结论或罗列风格都不得分。

**例题 2**：与高项论文相比，架构论文最突出的要求是？
A. 字数更多　B. 体现技术选型理由与关键技术机制（技术深度）　C. 不需要项目背景　D. 只写管理过程
**答案 B**。解析：架构论文强调技术方案的深度与合理性（选型理由、机制、量化效果）；项目背景仍必需，管理过程只是背景衬托。

## ⚠️ 易错提醒

- 案例"选型对比题"**必须给对比维度**，只下结论会失分；
- 论文**只谈技术不谈项目**（或只谈管理不谈技术）都会明显扣分；
- 写量化效果时数字要自洽（如"QPS 从 500 提升到 5000"，别与系统规模矛盾）；
- 提纲务必先写：120 分钟里列提纲 10–15 分钟能显著降低跑题风险。
